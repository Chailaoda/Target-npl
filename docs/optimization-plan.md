# Target-npl 优化方案（架构师报告）

---

## 零、先于方案的判断：你可能把症状当成了原因

你描述的问题是"运行一段时间自己就停了"和"运行到一定量就停了"。但这些是**症状**，不是原因。

**真正的原因有三层**：

1. **设计层面**：系统从一开始就不是"持续运行"的架构。它是"单次任务执行器"——每次触发一个任务，任务完成就退出。这不是 bug，是设计意图。你要的是一个**守护进程**，但你建了一个**命令行工具**。

2. **资源层面**：500 次 API 调用硬上限、10 次连续错误断路器、单浏览器会话——这些都是**有意设计的安全边界**，不是缺陷。它们在保护你不被平台封号、不烧穿 API 预算。去掉它们不是优化，是去掉刹车。

3. **目标层面**：你说"持续抓取、持续运行"，但你真正要的不是 7×24 爬虫。你要的是**持续发现符合兴趣的新账号**。这两个目标的最优架构完全不同。前者是爬虫工程问题，后者是**信息检索 + 增量更新**问题。

> **结论**：最值得解决的问题不在你列出的 7 个堵点里。最值得解决的是：**从"单次批量执行"到"增量持续发现"的架构范式转换**。

## 一、比 A-G 更值得解决的问题

### H. 没有增量去重机制

当前每次运行从零开始搜索。同样的关键词 + 同样的平台 = 大量重复内容。你在浪费采集预算和 API 调用去处理已经见过的东西。

**跨领域参考**：搜索引擎爬虫（Googlebot）不会每次都重新爬整个互联网。它维护一个 URL frontier，只爬新的或已过期的页面。

### I. 兴趣画像只依赖文本字面匹配

`interest_service.py` 的 `analyze_text()` 只做字面匹配（`_contains()` 函数）。如果用户讨论的话题没有命中你定义的关键词/别名，就会被判为 `not_relevant`。对于很多兴趣社群来说，行话、暗语、缩写是主要表达方式——字面匹配会错过大量真实信号。

**跨领域参考**：推荐系统中的协同过滤——不需要理解内容语义，只要"和已知目标人群有相似行为的人"就是候选。

### J. 账号发现只走"搜索"这一条路

当前唯一的发现路径是：关键词 → 平台搜索 → 帖子 → 评论 → 作者。但社交平台的**图关系**（关注、互动、同好群组）是更有效的发现渠道。一个确认的目标用户的关注列表里，很可能有更多目标用户。

**跨领域参考**：社交网络分析中的"雪球抽样"（snowball sampling）和 community detection。

## 方案一：渐进优化路线（最小改动，最快见效）

### 设计哲学

> **不动架构，只补调度和去重——用最小改动让当前系统"转起来"。**

### 架构蓝图

```
当前架构不变，仅新增：
  ┌─────────────────┐
  │  Scheduler       │ ← Windows Task Scheduler / 简单 Python 守护进程
  │  (定时触发)       │
  └────────┬────────┘
           │ 每 N 分钟触发一次
           ▼
  ┌─────────────────┐
  │  Task Router     │ ← 新模块：选择下一个该运行的平台/关键词组合
  │  (任务路由)       │    基于"上次运行时间"+"上次成功率"
  └────────┬────────┘
           │
           ▼
  ┌─────────────────┐
  │  现有 Pipeline   │ ← task_service → task_worker → workflow
  │  (单次执行)       │    不改动
  └────────┬────────┘
           │ 完成后写入结果
           ▼
  ┌─────────────────┐
  │  Dedup Index     │ ← 新模块：content_id 布隆过滤器
  │  (去重索引)       │    跳过已采集的内容
  └─────────────────┘
```

### 解决堵点

| 堵点 | 策略 |
|------|------|
| A. 非持续 | Scheduler 定时触发，每次跑一个小批次（1 个平台 × 2-3 个关键词），间隔 15-30 分钟 |
| B. 单任务互斥 | **不改**。互斥锁其实是正确的——你不需要同时跑多个任务，你需要的是任务排队轮转 |
| C. 平台串行 | 拆成多个小任务，每次只跑一个平台。Scheduler 轮转平台 |
| D. 收集-分析耦合 | 分两阶段调度：先收集轮（只收集不分析），积累到一定量后触发分析轮 |
| E. 浏览器脆弱 | 在 Scheduler 层加健康检查：采集前验证 CDP 连接，失败则跳过该平台并通知用户 |
| F. 错误恢复 | 断路器不改。Scheduler 记录平台健康状态，对失败率高的平台自动降低调度频率 |
| G. 无调度 | Scheduler 本身就是解决方案 |

### 实施路径

**阶段 1（1-2 天）**：
- 新建 `scheduler.py`：基于 `sched` 或 `APScheduler` 的简单定时器
- 实现平台轮转逻辑
- 用 Windows Task Scheduler 作为守活机制

**阶段 2（1-2 天）**：
- 新建 `dedup.py`：基于 SQLite 的 content_id 去重表
- 在采集入口处跳过已见内容
- 添加"上次采集时间"记录

**阶段 3（1 天）**：
- 收集/分析解耦：收集完成后写标记文件，分析任务独立触发
- 浏览器健康检查

### 权衡与风险

- **优点**：改动量最小（< 500 行新代码），不动现有管线，风险低
- **缺点**：本质上是在批处理外面套了个循环，不是真正的流式处理。扩展到大量关键词时调度延迟会增大
- **风险**：Windows Task Scheduler 的可靠性取决于系统休眠/重启策略

### 预期效果

- 从"手动触发单次运行"→"自动持续运行，每 15-30 分钟一轮"
- 去重后 API 调用利用率预计提升 2-5 倍（取决于关键词重叠度）
- 单日可处理量从当前的 ~500 次 API 调用 → ~12000 次（24h × 24 轮/h ÷ 2 × 500）

## 方案二：流式管线路线（中等改动，根本解耦）

### 设计哲学

> **把"大任务单次执行"拆成"小任务流式处理"——内容一进来就立即分析，不等批次完成。**

### 架构蓝图

```
  ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
  │  Collector Pool  │     │  Content Queue   │     │  Analyzer Pool  │
  │  (采集器池)       │────▶│  (内容队列)       │────▶│  (分析器池)      │
  │  每平台独立进程    │     │  SQLite WAL 表    │     │  独立消费进程     │
  └────────┬────────┘     └─────────────────┘     └────────┬────────┘
           │                                               │
           │ 浏览器会话隔离                                   │ 结果写入
           ▼                                               ▼
  ┌─────────────────┐                             ┌─────────────────┐
  │  Session Manager │                             │  Profile Builder │
  │  (会话管理器)     │                             │  (画像构建器)     │
  │  心跳 + 自动恢复  │                             │  增量更新账号画像  │
  └─────────────────┘                             └─────────────────┘

  上层：Orchestrator（编排器）
  - 管理采集器池的生命周期
  - 控制全局速率和预算
  - 响应 control_server 的配置变更
```

### 核心设计：Content Queue

这是方案的关键抽象。用 SQLite WAL 模式实现一个轻量级消息队列：

```
content_queue 表:
  id INTEGER PRIMARY KEY
  platform TEXT
  content_id TEXT  
  source_hash TEXT (去重键)
  raw_json TEXT
  status TEXT  -- 'pending' | 'analyzing' | 'done' | 'failed'
  enqueued_at TEXT
  claimed_at TEXT
  attempts INTEGER DEFAULT 0
```

**跨领域参考**：这是 Kafka 的核心模式——生产者/消费者解耦。但这里不需要 Kafka 的复杂性，SQLite WAL 完全能胜任当前数据量级（百/千级别 TPS）。

### 解决堵点

| 堵点 | 策略 |
|------|------|
| A. 非持续 | Orchestrator 是守护进程，永远运行。采集和分析是独立的持续循环 |
| B. 单任务互斥 | **替换为细粒度锁**：每个平台一把锁，分析器有独立的并发控制 |
| C. 平台串行 | Collector Pool 中每个平台是独立进程，真正并行 |
| D. 收集-分析耦合 | Queue 完全解耦。内容入队即可，分析器按自己的节奏消费 |
| E. 浏览器脆弱 | Session Manager 维护心跳，检测到断连后自动重启浏览器进程（不重新登录——保留 profile 目录） |
| F. 错误恢复 | 分析失败的内容回到队列，指数退避重试（max 3 次）。按平台独立断路：一个平台炸了不影响其他 |
| G. 无调度 | Orchestrator 本身是调度器，可配置各平台的采集间隔和关键词轮转策略 |

### 实施路径

**阶段 1（2-3 天）**：
- 新建 `content_queue.py`：SQLite WAL 队列
- 重构 `multi_collection.py` → 采集结果入队而非直接写 raw.jsonl
- 新建 `analyzer_worker.py`：从队列消费并调用现有 `workflow.run()` 的核心逻辑

**阶段 2（2-3 天）**：
- 新建 `orchestrator.py`：采集器池管理
- 新建 `session_manager.py`：浏览器会话心跳 + 恢复
- 平台并行化

**阶段 3（1-2 天）**：
- 增量画像更新：分析完一条就更新相关账号的 interest_profile
- Orchestrator 通过 control_server API 接受配置热更新

**阶段 4（1 天）**：
- 全局预算控制器（跨平台共享日预算）
- 监控仪表盘：队列深度、各平台健康状态、API 消耗速率

### 权衡与风险

- **优点**：真正的流式处理，收集和分析完全解耦，平台故障隔离。架构可扩展性好
- **缺点**：改动量中等（~1500-2000 行），需要仔细处理 SQLite 并发（WAL 模式）
- **风险**：SQLite 在高并发写入下可能出现 `SQLITE_BUSY`，需要合理的重试策略。7 个平台同时写入 + 分析器读取是可行的，但需要测试

### 预期效果

- 从"串行批处理"→"多平台并行采集 + 实时分析"
- 单个平台故障不影响整体运行
- 采集到分析的延迟从"等整批完成"→"秒级"
- 单日吞吐量理论上限：7 平台 × 每平台每轮 100 帖 × 每天 48 轮 = ~33600 条原始内容

## 方案三：智能发现路线（重新定义问题）

### 设计哲学

> **不要更快地爬——要更聪明地找。从"关键词搜索"扩展到"社交图谱 + 行为相似度"的多维发现。**

### 核心洞察

当前系统的发现路径是：

```
关键词 → 搜索结果 → 帖子 → 评论者 → 账号
```

这条路径有两个根本限制：
1. **搜索结果有限且重复**：同样的关键词翻页到后面质量急剧下降
2. **只能发现"说了关键词的人"**：但很多目标人群从不在公开内容里使用你定义的关键词

**更有效的发现路径**：

```
路径 1（当前）：关键词 → 搜索 → 帖子 → 评论 → 账号
路径 2（新增）：已确认账号 → 互动对象 → 候选账号  ← 雪球扩展
路径 3（新增）：已确认账号 → 相似内容 → 新帖子 → 新账号  ← 平台推荐利用
路径 4（新增）：高质量帖子 → 深度评论区 → 活跃参与者  ← 社区挖掘
```

**跨领域参考**：
- **推荐系统**中的 user-based / item-based 协同过滤
- **社交网络分析**中的 community detection 和 influence propagation
- **搜索引擎**的 PageRank——链接结构比内容关键词更能说明页面重要性

### 架构蓝图

```
  ┌───────────────────────────────────────────────────────┐
  │                    Discovery Engine                    │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌───────┐ │
  │  │ Keyword   │  │ Social   │  │ Content  │  │ Deep  │ │
  │  │ Search    │  │ Graph    │  │ Similar  │  │ Thread│ │
  │  │ (当前)    │  │ Explorer │  │ Finder   │  │ Miner │ │
  │  └────┬─────┘  └────┬─────┘  └────┬─────┘  └───┬───┘ │
  │       └──────────────┴─────────────┴────────────┘     │
  │                        │                               │
  │                   Candidate Pool                       │
  │               (候选账号 + 置信度打分)                     │
  └───────────────────────┬───────────────────────────────┘
                          │
                          ▼
  ┌─────────────────┐          ┌─────────────────┐
  │  Content Queue   │          │  Interest        │
  │  (方案二的队列)   │          │  Profiler        │
  │                  │          │  (强化版画像)      │
  └────────┬────────┘          └────────┬────────┘
           │                            │
           ▼                            ▼
  ┌─────────────────┐          ┌─────────────────┐
  │  Analyzer        │          │  Feedback Loop   │
  │  (分析器)         │          │  (反馈循环)       │
  │                  │          │  "好的发现"反哺    │
  └─────────────────┘          │  发现策略权重      │
                               └─────────────────┘
```

### 新增发现模块

**Social Graph Explorer（社交图谱探索器）**：
- 输入：已确认的高置信度目标账号
- 动作：访问其主页 → 获取其公开互动对象（评论互动、@提及）
- 输出：候选账号列表 + "与已知目标的关系强度"
- 限制：不获取关注列表（大多数平台不公开），只用公开互动数据

**Content Similarity Finder（内容相似发现器）**：
- 输入：已确认的高质量帖子
- 动作：利用平台"相关推荐"API 或搜索帖子标题的变体
- 输出：相似内容 + 其作者/评论者

**Deep Thread Miner（深度评论区挖掘器）**：
- 输入：高质量帖子（有很多评论的）
- 动作：深度翻阅评论区（当前 `comments_per_post=100` 限制太低）
- 输出：评论区活跃参与者

**Feedback Loop（反馈循环）**：
- 当 InterestService 确认一个账号有高兴趣分时，该账号进入 Social Graph Explorer 的输入
- 发现效率高的路径（平台 × 策略）自动获得更多预算
- 发现效率低的路径自动降权

### 解决堵点

| 堵点 | 策略 |
|------|------|
| A. 非持续 | 以方案二的 Orchestrator 为基础，加上发现引擎的持续循环 |
| B. 单任务互斥 | 同方案二，细粒度锁 |
| C. 平台串行 | 同方案二，多平台并行 |
| D. 收集-分析耦合 | 同方案二，Queue 解耦 |
| E. 浏览器脆弱 | 同方案二，Session Manager |
| F. 错误恢复 | 同方案二，加上发现策略层面的自适应——某条路径持续失败就降权 |
| G. 无调度 | Orchestrator + Discovery Engine 双循环 |
| **H. 无增量去重** | Candidate Pool 维护全局已见集合 |
| **I. 字面匹配局限** | 社交图谱和行为相似度不依赖关键词匹配 |
| **J. 单一发现路径** | 四条发现路径并行 |

### 实施路径

**阶段 1（方案二的阶段 1-2，4-5 天）**：
- 先建好流式管线基础（Queue + Orchestrator + Session Manager）

**阶段 2（3-4 天）**：
- Candidate Pool + 置信度打分
- Deep Thread Miner（最容易实现：只是把 comments_per_post 提高 + 分页翻阅）

**阶段 3（3-4 天）**：
- Social Graph Explorer（需要新的平台适配：访问用户主页 → 获取其作品列表 → 获取互动者）
- 反馈循环原型

**阶段 4（2-3 天）**：
- Content Similarity Finder
- 发现策略权重自适应

**阶段 5（2 天）**：
- 强化版 Interest Profiler：在字面匹配之外，加入"社交距离"和"行为相似度"作为辅助信号
- 仪表盘：各路径的发现效率、候选池深度、确认率

### 权衡与风险

- **优点**：从根本上解决"发现效率"问题。同样的采集预算能发现多 3-10 倍的目标账号
- **缺点**：改动量大（~4000-5000 行），需要新的平台适配工作，实施周期 2-3 周
- **风险**：
  - 社交图谱探索需要更多平台请求，可能触发反爬
  - 雪球扩展需要防止"漂移"——离初始社群越来越远
  - 需要仔细的速率控制，避免对单个用户主页的密集访问

### 预期效果

- 发现效率：从"纯搜索"的线性增长 → "搜索 + 图扩展"的指数级网络效应
- 同样的日请求预算下，预计目标账号发现量提升 3-10 倍
- 兴趣画像准确度提升：社交距离信号补充字面匹配的盲区
- 系统真正实现"越用越好"的正循环

## 推荐与对照

| 维度 | 方案一（渐进） | 方案二（流式） | 方案三（智能发现） |
|------|:---:|:---:|:---:|
| 改动量 | ~500 行 | ~2000 行 | ~5000 行 |
| 实施周期 | 3-5 天 | 6-9 天 | 15-20 天 |
| 解决"停止运行" | ✅ | ✅ | ✅ |
| 解决"重复采集" | ✅ | ✅ | ✅ |
| 多平台并行 | ❌（轮转） | ✅ | ✅ |
| 实时分析 | ❌ | ✅ | ✅ |
| 故障隔离 | 部分 | ✅ | ✅ |
| 发现效率提升 | 2-5× | 5-10× | 10-30× |
| 对现有代码的侵入性 | 低 | 中 | 高 |

### 我的推荐

**先做方案一，再迭代到方案二，最后按需加方案三的模块。**

原因：
1. 方案一能在 3-5 天内让系统"转起来"，解决你最紧迫的问题
2. 方案一的 Scheduler 和去重索引是方案二的前置基础，不会浪费
3. 方案二的 Queue 和 Orchestrator 是方案三的前置基础
4. 方案三的各个发现模块可以逐个加入，不需要一次性全部实现

**不建议直接跳到方案三**，因为在没有稳定运行的基础管线之前，高级发现策略的调试会非常痛苦。

## 附录：被高估的问题和被低估的问题

### 被高估的

- **"多平台并行"**：当前数据显示你主要在用抖音，其他平台甚至没有浏览器会话配置。先把单平台跑顺比追求 7 平台并行更实际
- **"500 次 API 上限"**：这个限制的真正问题不是数字太小，而是没有增量分析——如果你有去重，500 次/批 × 48 批/天 = 24000 次/天，对于个人使用完全足够

### 被低估的

- **增量去重**：这是投入产出比最高的单一改动。一行代码（`INSERT OR IGNORE` 到已见内容表）就能避免大量浪费
- **浏览器 profile 持久化**：当前的 CDP 连接模式意味着浏览器关闭就丢失登录态。一个稳定的 Chromium profile 目录 + 自动重启比复杂的会话恢复逻辑有效得多
- **"原始数据先留着"**：你在需求里提到了这个，但这其实是当前系统**已经在做**的事（raw.jsonl + checkpoint.json）。真正的问题是分析没有和采集解耦，导致你以为原始数据没保留
